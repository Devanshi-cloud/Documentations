**V0.dev Prompt - Full-Feature Structural Health Monitoring (SHM) Dashboard Built with Astro**  

*Goal:* Generate a production-ready SHM dashboard that runs on the Astro framework, delivers sub-second page loads, and uses the minimal-JavaScript, partial-hydration model Astro is known for [1].

---  

### 1. Project Overview  
Create a multi-page web application that monitors critical infrastructure (sensors, bridges, AI-vision inspections, surveillance cameras, and digital twins). The UI must be responsive, support dark/light mode, and comply with WCAG 2.1 AA. All data streams are real-time; historic data must be queryable for trend analysis. The system must enforce role-based access control (RBAC) and provide a robust alert/notification engine.

---  

### 2. Page Navigation & UI Design  

**Navigation hierarchy** (single-page navigation with Astro “client:only” islands where interactivity is required):  

- **Home / Dashboard Overview** - high-level status cards for Sensors, Bridges, AI Vision, Cameras, Digital Twin; global alerts banner.  
- **Sensors**  
  - *List view* - table with sensor name, type, health badge, last value, anomaly flag.  
  - *Detail view* - real-time line chart, heatmap of spatial distribution, health diagnostics panel, download CSV.  
- **Bridges**  
  - *Fleet view* - map of bridge locations, status summary.  
  - *Bridge detail* - load curve chart, structural integrity gauge, maintenance schedule calendar, damage assessment report with image overlays.  
- **AI Vision**  
  - *Inspection queue* - list of pending images/video clips.  
  - *Result viewer* - side-by-side raw media and AI-annotated output (crack polygons, defect confidence scores).  
- **Cameras & Surveillance**  
  - *Live wall* - grid of live video streams (WebRTC or HLS).  
  - *Stream detail* - motion-detection overlay, analytics timeline, export clip button.  
- **Digital Twin**  
  - *3-D model page* - interactive Three.js canvas synchronized with sensor data (color-coded stress heatmap).  
  - *Simulation panel* - sliders for load scenarios, “run prediction” button, results plotted on the model.  
- **Admin / Settings** - user management, role assignment, API key rotation, system health dashboard.

**Visual design guidelines**:  
- Use Tailwind CSS with `darkMode: 'class'` for manual toggle [2].  
- Grid layout: 12-column responsive grid; cards collapse to single column on < 640 px.  
- Typography: system fonts for speed, headings using `font-semibold`.  
- Icons: Heroicons (SVG) loaded as static assets (no runtime JS).  
- Accessibility: `aria-label` on all interactive islands, focus-visible outlines, sufficient contrast.

**Real-time visualizations**:  
- Primary chart library: ApexCharts for quick theme integration and low bundle size (preferred for most use cases per Astro docs) [1].  
- For custom or high-density charts, fallback to Chart.js (still compatible with Astro) [1].  
- Heatmaps rendered with D3.js inside a client-only component.  
- 3-D twin built with Three.js + React-Three-Fiber inside an Astro `client:only='react'` island [3].

### 3. Data Flow & Backend Architecture  

**Ingestion layer**  
- **Sensors** → MQTT broker (e.g., EMQX) publishing JSON payloads at 1-10 Hz.  
- **Cameras** → RTSP streams ingested by Amazon Kinesis Video Streams (KVS) and stored in S3 .  
- **AI Vision** → batch upload of images/video to an inference service (REST endpoint) that returns JSON annotations.

**Real-time transport**  
- Use **WebSocket** for bidirectional control (e.g., sensor command, camera PTZ) and **Server-Sent Events (SSE)** for unidirectional streaming of high-frequency telemetry (lighter footprint, automatic reconnection) [4].  
- Astro SSR endpoint (`src/api/stream.ts`) creates a `ReadableStream` that pushes SSE events to the client.

**Caching & fallback**  
- Browser IndexedDB stores the last 5 minutes of sensor data for offline view; on reconnection, client sends a “sync” request with the last timestamp.  
- Video playback falls back to stored MP4 fragments in S3 when live feed drops.

**Storage**  
- Time-series sensor data → InfluxDB (high-write performance, native MQTT-Telegraf pipeline) [5].  
- Historical bridge load data → TimescaleDB (SQL analytics, retention policies) [6].  
- AI inference results → PostgreSQL JSONB tables for flexible queries.  
- Video archives → S3 bucket with lifecycle policies.  
- 3-D model states & simulation parameters → DynamoDB (key-value, low latency).

**Backend services**  
- **API gateway** (Node.js + Fastify) exposing versioned REST endpoints (`/api/v1/sensors`, `/api/v1/bridges`, `/api/v1/ai`, `/api/v1/cameras`, `/api/v1/digital-twin`).  
- **Authentication** via OAuth2/OIDC (Auth0) returning JWTs; JWT includes role claim [7].  
- **Rate limiting** with exponential backoff (429 handling) per Astro API best practices [8].  
- **Message broker** (Redis Streams) for fan-out of alerts to SSE, email, and push services.

### 4. User Roles & Access Control  

| Role | Permissions | Typical Users |
|------|-------------|---------------|
| **Viewer** | Read-only access to dashboards, live video (no controls) | Public stakeholders |
| **Analyst** | View + export data, run ad-hoc queries, acknowledge alerts | Data scientists |
| **Engineer** | All Analyst rights + edit sensor thresholds, schedule maintenance, trigger simulations | Structural engineers |
| **Security Operator** | Access to camera controls, motion-detection config, audit logs | Facility security |
| **Administrator** | Full CRUD on users, roles, API keys, system settings | IT admins |

RBAC enforcement occurs in the API layer (JWT `role` claim) and is mirrored in Astro client islands by conditionally rendering UI components (`{user.role === 'Engineer' && <Button …/>}`). All communications are TLS-encrypted; sensitive data at rest is encrypted using KMS-managed keys. Audit logs are written to CloudWatch Logs with immutable retention.

### 5. Alert & Notification System  

**Detection algorithms**  
- Sensor anomaly detection: statistical process control (3-sigma) plus machine-learning model (auto-encoder) trained on historic data (see SHM anomaly detection literature) [9].  
- Bridge load breach: rule-based thresholds (e.g., > 80 % design load).  
- AI Vision defects: confidence > 0.85 on crack classification triggers “defect” alert.  
- Motion detection: background subtraction on video frames; persistent motion > 5 s triggers security alert.

**Notification channels**  
- In-app toast (Sonner) for immediate feedback.  
- Email via SendGrid.  
- SMS via Twilio.  
- Push notifications (Web Push API) for mobile browsers.

**Alert UI**  
- Global banner on the Overview page with severity color.  
- Dedicated “Alerts” page with filterable table, pagination, and “assign” dropdown.  
- Historical incident log exported as CSV.

**Escalation workflow**  
1. Alert created → assigned to Engineer.  
2. If not acknowledged within 15 min → escalates to Administrator via email/SMS.  
3. After 1 hour without resolution → creates a ticket in external CMMS (REST webhook).

### 6. Performance & Optimization (Astro-Centric)  

- **Static Generation**: All static pages (Help, About, Settings) built at build time.  
- **Partial Hydration**: Only interactive islands (charts, video players, 3-D canvas) marked `client:load` or `client:only='react'` to avoid shipping JavaScript for the rest of the page [1].  
- **Code Splitting**: Dynamic imports for heavy libraries (Three.js, Chart.js) so they load only when the user navigates to the corresponding page.  
- **Lazy Loading**: Video streams use `loading="lazy"` and are only instantiated when the user scrolls into view.  
- **CDN Edge Caching**: Astro output (`dist/`) deployed to a CDN (e.g., Cloudflare Workers) with `Cache-Control: max-age=31536000` for static assets; SSE endpoints are excluded from caching.  
- **Asset Optimization**: Images compressed with AVIF/WebP; CSS purged via Tailwind’s JIT mode.

### 7. Mobile Responsiveness & Cross-Device Support  

- Breakpoints: `sm` (640 px), `md` (768 px), `lg` (1024 px).  
- Touch-friendly controls: larger hit-targets (≥ 44 px), swipe gestures for carousel of video feeds, pinch-to-zoom on the 3-D twin (Three.js built-in controls).  
- Off-canvas navigation drawer for phones, persisted top bar for tablets.  
- Performance budget: < 200 KB JavaScript per interactive page on mobile (measured via Lighthouse).

---  

### 8. Edge Cases & Failure Handling  

- **Sensor/network loss**: UI shows “offline” badge, retains last known value from IndexedDB, and triggers a “sensor disconnected” alert.  
- **Video feed interruption**: Player displays placeholder image with “Reconnecting…” overlay; after 3 attempts, switches to archived clip.  
- **AI model downtime**: Inference service returns 503; UI falls back to “pending review” status and queues the media for later processing.  
- **WebSocket disconnect**: Automatic exponential-backoff reconnection (max 30 s) with UI status indicator [10].  
- **CDN cache purge failure**: Fallback to origin fetch with `Cache-Control: no-cache`.

### 9. Integration & Tooling Recommendations  

- **Astro integrations**: `@astrojs/react` for React-Three-Fiber, `@astrojs/tailwind` for styling, `@astrojs/vercel` or `@astrojs/cloudflare` for edge deployment.  
- **Real-time**: `socket.io` (fallback to SSE) for bidirectional control; `eventsource-polyfill` for older browsers.  
- **CI/CD**: GitHub Actions workflow that runs `npm run build`, lints with `eslint`, runs `astro check`, and deploys to Cloudflare Pages (or Astronomer CI/CD for Airflow-backed pipelines) [11][12].  
- **Testing**: Cypress for end-to-end UI tests, Jest for unit tests of data adapters, and AstroFarm for real-device testing of video playback on low-end hardware [12].  
- **Monitoring**: Prometheus + Grafana for backend metrics; client-side performance measured with Web Vitals.

### 10. Deliverables for V0.dev  

1. **Project scaffolding** - Astro project with Tailwind, React integration, and TypeScript.  
2. **Folder structure** - `src/pages/` for each top-level view, `src/components/` for reusable islands (ChartCard, SensorTable, VideoTile, TwinCanvas), `src/api/` for SSE and REST endpoints.  
3. **Data adapters** - MQTT client (Node.js) pushing to InfluxDB, video ingest service writing to S3/KVS, AI inference wrapper exposing `/api/v1/ai/inspect`.  
4. **Auth middleware** - JWT verification, role guard, rate-limit handler.  
5. **Alert engine** - Node.js service consuming Redis streams, evaluating rules, emitting SSE events and webhook notifications.  
6. **Deployment scripts** - `astro build && astro preview` for local dev; GitHub Actions file (`.github/workflows/deploy.yml`) that builds, runs tests, and deploys to Cloudflare Pages with edge caching.

*The above specification, when fed to V0.dev, should result in a production-grade SHM dashboard that meets all functional, performance, security, and usability requirements while fully exploiting Astro’s static-site generation and minimal-JS philosophy.*

### 11. Validation & Credit-Efficiency Requirements

Before consuming any paid API credits, cloud resources, inference quotas, or third-party service usage, the system must validate all functionality using local mocks, test fixtures, and sandbox environments wherever possible.

**Mandatory pre-production validation:**

* Test all UI flows, API integrations, authentication, RBAC permissions, alert workflows, SSE streams, WebSocket reconnection logic, and database adapters using mocked data before connecting to production services.
* Verify all environment variables, credentials, and service endpoints prior to initiating paid requests.
* Execute automated unit, integration, and end-to-end test suites before any operation that incurs usage-based costs.
* Use local emulators, sample datasets, mocked MQTT streams, simulated camera feeds, and synthetic AI inference responses during development and QA.
* Perform a dry-run validation step before deploying infrastructure changes or triggering large-scale ingestion, video processing, AI inference, or simulation workloads.
* Generate a pre-flight checklist report confirming that all critical paths have passed testing before consuming production credits.
* Any feature that fails validation must be blocked from using paid resources until the issue is resolved and the test suite passes successfully.

**Guiding principle:** Test everything beforehand before consuming credits, compute resources, API quotas, inference tokens, storage operations, or any other billable infrastructure.
