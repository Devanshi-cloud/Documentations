# Module 2 Continued: Software Quality, Defects, Reliability & Role of Testing

# Software Quality
I define **software quality** as the degree to which software meets:
- specified requirements
- implied user needs

For me, quality means the software is **fit for purpose**, not just bug-free.

### Why quality matters:
- better user satisfaction
- reduced maintenance cost
- improved product reputation

---

# Software Defect
I define a **software defect** as a deviation from expected behavior.

I remember this chain:

**Error → Defect → Failure**

Where:
- **Error** = human mistake
- **Defect** = flaw in code/design
- **Failure** = visible issue seen by user

Example:
wrong code → button fails → app crashes

---

# Defect Management Process
My defect lifecycle is:

1. **Discover**
   - I identify the defect.
   - I log it in a bug tracking tool.

2. **Assign & Analyze**
   - Developer receives and analyzes it.

3. **Fix & Test**
   - Developer fixes it.
   - I retest it.

4. **Close**
   - Once verified, I close the defect.

Flow:
**Discover → Assign → Fix → Retest → Close**

---

# Software Reliability
I define **software reliability** as:

The probability that software performs correctly **without failure**
for a specified time in a specified environment.

Simple meaning:
- **Quality** = overall excellence
- **Reliability** = consistency over time

Example:
A premium car may have good quality,
but if it breaks often, it is not reliable.

---

# Common Types of Defects

## Functional Defects
Feature does not work correctly.
Example: login button fails.

---

## Performance Defects
Software is too slow.
Example: page loads very late.

---

## Usability Defects
UI is confusing or hard to use.

---

## Security Defects
System has vulnerabilities.
Example: risk of data breach.

---

# Measuring Quality & Reliability

## 1. MTTF (Mean Time To Failure)
I measure average time between failures.

Rule:
Higher MTTF = better reliability

---

## 2. Defect Density
I measure:

Defects per KLOC

Rule:
Lower defect density = better quality

---

## 3. Customer Satisfaction
I measure:
- feedback
- ratings
- reviews

Higher satisfaction = better quality

---

## 4. Post-Release Defects
I count how many bugs users find after release.

Rule:
Fewer post-release defects = stronger testing

---

# Role of Testing

I define **testing** as my primary activity for finding defects.

Testing belongs to **Quality Control (QC)**.

QC means:
- reactive
- detect problems
- fix problems

Simple:
**QC = detect and correct**

---

# Quality Assurance (QA)

I define **QA** as a proactive process.

Its purpose:
- define standards
- improve process
- prevent defects before they happen

Simple:
**QA = prevent and improve**

---

# QA vs QC

| QA | QC |
|---|---|
| proactive | reactive |
| prevents defects | finds defects |
| process focused | product focused |

---

# Final Conclusion

My ultimate goal is **software quality**.

I use **reliability** as a key indicator of that quality.

**Defects** are obstacles I must identify and remove.

That is why I always need:

**Strong Testing + Strong QA = Reliable Software**
